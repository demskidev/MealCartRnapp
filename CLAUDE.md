# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Meal Cart** — an Expo / React Native app (Expo SDK 54, RN 0.81, React 19, New Architecture) for meal planning, meal plans, and shopping lists, with a **Kroger** grocery integration. The backend is entirely **Firebase** (Auth, Firestore, Storage, Cloud Functions, Hosting).

## Commands

```bash
# App (Metro bundler / dev client)
npm start                 # expo start
npm run ios               # expo run:ios      (builds + runs native)
npm run android           # expo run:android
npm run web               # expo start --web

npm run lint              # expo lint (ESLint flat config, eslint-config-expo)
npx tsc --noEmit          # type-check (strict mode; no dedicated script)

# Cloud Functions (run from ./functions)
cd functions
npm run serve             # firebase emulators:start --only functions,hosting
npm run deploy            # firebase deploy --only functions,hosting
```

- **This is NOT an Expo Go project.** It uses native modules, a custom config plugin (`plugins/withGoogleSignInIOS.js` — Google/bundle URL schemes + Podfile/AppDelegate tweaks), and `newArchEnabled`, so it requires a **dev client** (`expo-dev-client`). Use `expo run:ios/android` or an EAS build (profiles in `eas.json`).
- `ios/` and `android/` are **gitignored** — they are generated by `expo prebuild` from `app.json`. Never hand-edit them; change `app.json` or the plugin instead.
- **No test framework is configured** (there is no `test` script). Do not assume Jest/RTL exist. With no tests, `npx tsc --noEmit` is the only automated check — it currently reports **~8 pre-existing** errors (`IntroScreen.tsx`, `AddItemToList.tsx`, `FilterModal.tsx`, `ProgressBar.tsx`, `appleSignin.ts`, `assets/svg/IconUpDown.tsx`), so filter to the files you touched.
- **`npm run reset-project` is the untouched create-expo-app starter script — it moves `app/` aside and scaffolds a blank one. Never run it.** `README.md` is likewise unmodified boilerplate and describes nothing about this app; ignore it.
- **React Compiler is on** (`experiments.reactCompiler` in `app.json`). Don't add `useMemo`/`useCallback` purely for memoization, and be aware that mutating values captured in render can behave differently than in an uncompiled build.
- OTA updates are configured (`expo-updates`, `runtimeVersion.policy: "appVersion"`), so a JS-only change ships to installed builds via EAS Update while native changes need a new build. **But every build made before 2026-08-13 has `channel: null`** (`eas.json` defined no `channel` until then), and `eas update` can only reach a build that carries a channel. So the 1.0.0 builds already in the stores and on testers' devices can *not* be hotfixed — they need a new build and release. Builds made from the current `eas.json` onward are reachable via `eas update --branch <development|preview|production>`. Verify with `eas build:list --json` before promising a JS-only fix can ship OTA.

### Android signing fingerprints & Google Sign-In

Google Sign-In on Android authenticates the *app*, not just the user: Play services checks `(package name, signing certificate SHA-1, OAuth client)` locally and fails with `DEVELOPER_ERROR` (status code `10`, surfaced by the native module as `error.code === "10"`) before any network call. So it is **deterministic per build, never flaky** — an intermittent report means different builds, not a race.

Every certificate that ever signs the app therefore needs its SHA-1 registered on the Firebase Android app `com.app.mealcart` (`1:107165390600:android:49c72691b58601b005febd`). Currently registered:

| SHA-1 | Signs |
| --- | --- |
| `a741c507bca1acf510198bac94f7fd0a2a7517c8` | Google Play app signing key — every install from any Play track |
| `fa87b9eb2a48a9ce1f163d39bd6d181c820da515` | EAS upload keystore — `preview` / `development` APKs |
| `720246de7f9d5c460fe1c02bd612fde62dc13e1f` | one developer's local `~/.android/debug.keystore` (`expo run:android`) |

- **`.aab`s are re-signed by Google Play**, so the upload key's SHA-1 does *not* cover store installs — the Play app signing key (Play Console → Protected with Play → App signing) is a separate fingerprint and must be added too. This was the cause of production Google Sign-In failing while EAS internal builds worked.
- **Each developer's debug keystore is unique to their machine**, so `expo run:android` needs that machine's SHA-1 added: `keytool -list -v -keystore ~/.android/debug.keystore -alias androiddebugkey -storepass android`.
- Registration is **server-side and takes effect without a rebuild** (the client authenticates with `webClientId`, so `google-services.json` is not consulted for this). `firebase apps:android:sha:create <appId> <sha1>` / `:list` manage it; re-download `google-services.json` afterwards only to keep the repo in sync.
- The project also contains a stale second Android app for the old package `com.jbehl23.mealcart` (`…android:359e7590045873b305febd`) and a stale second iOS app. Adding fingerprints to the wrong app looks like a fix and changes nothing.
- **iOS has no certificate binding** — Google Sign-In there keys off the bundle id and the reversed-client-id URL scheme (`iosUrlScheme` in `app.json`, `IOS_CLIENT_ID` in `services/googleSignIn.ts`, `REVERSED_CLIENT_ID` in `GoogleService-Info.plist` — all three must agree). `DEVELOPER_ERROR` is Android-only.

### Patched dependencies (`patch-package`)

`postinstall` runs `patch-package`; patches live in `patches/` (currently `rn-tourguide`). Run `npm install` after pulling to reapply. To change a patched package:

```bash
# 1. edit the file under node_modules/<pkg>/...
npx patch-package rn-tourguide   # 2. regenerate patches/<pkg>+<version>.patch — MUST run from the repo root
npx expo start --clear           # 3. Metro caches node_modules; a plain restart is not enough
```

- Regenerating **overwrites the whole patch file**, so always verify existing hunks survived (`grep '^diff --git' patches/*.patch`) before committing.
- `node_modules/` is gitignored — only `patches/` is tracked, so teammates need `npm install` to pick a patch up.
- `rn-tourguide` ships **compiled `lib/` only** (`main: lib/index.js`, no `src/`), so patch `lib/components/*.js`.

## Architecture

### Navigation — expo-router gated by Redux (hybrid, non-obvious)

Entry is `expo-router/entry` → `app/_layout.tsx` (`RootLayout`), which mounts all providers (Redux `Provider`, `TourStepProvider`, `TourGuideProvider`, `KeyboardProvider`, `FontProvider`) and renders `navigation/RootNavigator.tsx`.

Rather than gating auth through the file tree, `RootNavigator` reads `auth.isAuthenticated` from Redux and renders **either** `AuthNavigator` **or** `AppNavigator`, each a plain expo-router `<Stack>`. So:

- Screens physically live under `app/`: `app/screens/*` (auth flow), `app/(tabs)/*` (main tabs + nested `home/`), `app/appscreens/*` (detail/modal screens).
- **`<Stack.Screen>` registration is per-screen options, not a whitelist.** expo-router routes every file under `app/` regardless, and many existing registrations use names that don't match their route (`AuthNavigator` lists `"SignIn"` for `app/screens/SignIn.tsx`; `AppNavigator` lists `"CreateMealPlan"` for `app/appscreens/CreateMealPlan.tsx`; `app/(tabs)/home/_layout.tsx` lists `"HomeScreen"`/`"DietaryPreferencesScreen"` for files named `index.tsx`/`DietaryPreferences.tsx`). Those entries are inert. A new screen works from the file alone — register it only if you need options, and then use the **real** route name.
- Navigate with the helpers in `utils/Navigation.ts` (`pushNavigation`, `replaceNavigation`, `resetAndNavigate`, `backNavigation`) using the route constants in `constants/AppRoutes.ts` (`APP_ROUTES`) — not raw `router` calls or string paths. `APP_ROUTES` also has stale entries (e.g. `FIRST_SCREEN` → a nonexistent `/screens/FirstScreen`), and not every screen is listed, so verify a constant before trusting it.
- Typed routes are enabled, but the helpers cast to `any` — so a wrong path is a runtime no-op, not a type error.

### State — Redux Toolkit + redux-persist

- Store: `reduxStore/store.ts`. Slices: `auth`, `home`, `ingredientCategory`, `meal`, `profile`, `plans`, `shopping`.
- **Only the `auth` slice is persisted** (redux-persist whitelist, AsyncStorage backend).
- The `LOGOUT` action resets the **entire** store (root reducer sets `state = undefined`).
- `serializableCheck` is **disabled** (Firestore Timestamps/Dates flow through state).
- Always use the typed hooks from `reduxStore/hooks.ts`: `useAppDispatch`, `useAppSelector`.
- Constants are centralized: action-type/slice-name strings in `reduxStore/actionTypes.ts`; Firestore collection names, form field keys, and enums in `reduxStore/appKeys.ts`.

### MVVM layering

Data flows **View → ViewModel → Slice thunk → Service → Firebase**. Respect these boundaries:

- **Slices** (`reduxStore/slices/*`) contain `createAsyncThunk`s that hold business logic and call services. This is the model layer.
- **ViewModels** (`viewmodels/*ViewModel.ts`) are custom hooks (e.g. `useMealsViewModel`) that select state and expose action wrappers. Convention: wrappers take **`onSuccess`/`onError` callbacks** and inspect `thunk.fulfilled.match(resultAction)`. Screens consume viewmodels, never slices/services directly.
- **Services** (`services/*`) are thin Firebase wrappers:
  - `firebase.ts` — initializes app/auth (AsyncStorage persistence)/`db`/`functions` (region `us-central1`)/`storage`. Firebase config is hardcoded here.
  - `firestore.ts` — generic CRUD + cursor pagination (`queryDocuments`), subcollection helpers, `uploadImageToFirebase`.
  - `waitForAuth.ts` — `waitForAuthReady` / `waitForAuthInitialized`; await these before server-backed flows that need `auth.currentUser` after a cold start.
  - `googleSignIn.ts`, `appleSignin.ts` — social auth.
  - `krogerApi.ts` — `httpsCallable` wrappers for the Cloud Functions, **plus some direct `fetch` calls to `api.kroger.com`** (see the Kroger section below).

### Firestore data model

Collection names live in `reduxStore/appKeys.ts`; access is enforced by `firestore.rules` (composite indexes in `firestore.indexes.json`).

- `meals/{id}` — owned by `uid`. **Global/official meals** use the sentinel `uid == "global"` (`GLOBAL_MEALS_UID`) + `isGlobal == true`, and are readable by every signed-in user.
- `mealIngredients/{mealId}` doc **+ `ingredients` subcollection** = the source of truth for a meal's ingredients, joined onto meals **client-side** by `enrichMealsWithIngredients` in `mealsSlice.ts`. An ingredient is either Kroger-linked (`isKroger`) or references `ingredientCategory`.
- `plans`, `shoppingList` — private per user (`uid`).
- `mealPlan` — per-user, plus shared defaults where `uid == ""`.
- `users/{uid}` — profile doc; document id **is** the auth uid.
- `ingredientCategory`, `ingredients`, `dietryPreferences` (note the misspelling — it's real) — shared read-only reference data, admin-writable only. The admin allowlist is an email list in `firestore.rules`.

### Plans & shopping-list domain rules (not derivable from types)

- **`MealStatus`** (`reduxStore/appKeys.ts`) is `CREATED | STARTED | RESUMED | PAUSED | COMPLETED`. There is **no `UPCOMING`** — "upcoming" is derived purely from `startDate` vs today.
- **Several plans may be `STARTED` at once** (so a user can pull a shopping list for a plan before it begins). `plans.activePlan` is still a *single* slot: it is the `STARTED` plan **whose `days[]` include today** (`pickActivePlanForToday` in `planSlice.ts`), and it is `null` when no started plan covers today. Home shows only that plan; the Plans tab renders **every** `STARTED` plan. Anything new that assumes one started plan will silently pick an arbitrary one.
- **Shopping-list items are untyped extras.** The runtime docs use an `ingredients` array whose fields (`acquired`, `isKroger`, `krogerIngredientId`, `count`) are **absent from the declared `ShoppingListItem` interface** — it declares `items`/`isChecked` instead. Trust the runtime shape written by `CreateNewListBottomSheet.tsx`, not the interface.
- In `TestPlanShopping.tsx`, checkbox selection is tracked as composite string ids (`${ingredientId}-${mealId}-${index}`) keyed to the **flat `allIngredients` index**, while `acquired` separately records what was already sent to Kroger. Keep those two concepts distinct: selection drives *what to send*, `acquired` drives the progress bar.

### Kroger integration (secrets server-side; some calls go direct)

**Secrets** (client id/secret) live only in Cloud Functions — but the app is *not* purely proxied. There are two paths, and it matters which you use:

1. **Via Cloud Functions** — OAuth, connection status, store selection, and generic requests through `krogerProxy`.
2. **Direct from the client** — `krogerApi.ts` fetches a short-lived user OAuth token via the `getKrogerUserToken` callable, then calls `https://api.kroger.com` **directly**: `GET /v1/cart`, and `PUT /v1/cart/add` in `addItemsToKrogerCart`. So cart writes do **not** pass through a function, and `functions/src/config.js`'s path allowlist (`/v1/cart`) does not constrain them.

- `index.js` exposes `createKrogerAuthSession`, `getKrogerConnectionStatus`, `krogerProxy`, `krogerOAuthCallback`, `getKrogerAppToken`, `getKrogerUserToken`, `saveKrogerSelectedStore`, `disconnectKrogerAccount`.
- `krogerAuth.js` (token lifecycle), `krogerApi.js` (server request wrapper), `config.js` (base URL, redirect URI, path allowlist).
- OAuth redirect `https://mealcart-5d62b.web.app/kroger/callback` is rewritten to the `krogerOAuthCallback` function via the Hosting rewrite in `firebase.json`, which then deep-links back into the app (scheme `mealcartrnmain`).
- Secrets are `defineSecret("KROGER_CLIENT_ID" / "KROGER_CLIENT_SECRET")`. See `docs/kroger-firebase-setup.md` and `docs/kroger-file-map.md`.

### Guided onboarding tour

First-run tour uses `rn-tourguide` (patched) coordinated by `context/TourStepContext.tsx`. Because tour steps must trigger UI actions across different screens, the context exposes many `triggerX` / `setTriggerX` callback-registration slots that screens populate on mount. Completion is tracked on `user.hasCompletedTour` (`markTourCompleted` in `authSlice.ts`).

Non-obvious details:

- **`zone` number *is* the step order, and content is index-based:** `TourGuideZone zone={N}` → `tourSteps[N - 1]` in `components/TourTooltip.tsx` (`stepIndex = currentStep.order - 1`). The tour spans zones 1–18 across `app/(tabs)/home/index.tsx`, `app/(tabs)/_layout.tsx`, `2_Plans.tsx`, `3_Lists.tsx`, `CreateMealPlan.tsx`, `CreateNewListBottomSheet.tsx`, `TestPlanShopping.tsx`. **Renumbering or inserting a zone silently reassigns every later step's text**, so keep zone numbers and the `tourSteps` array in lockstep.
- `TourTooltip.tsx` also drives **cross-screen navigation** per step (`handleNextOrNavigate` / `handleBackOrNavigate` switch on `stepIndex`) — so it is control flow, not just presentation.
- **Tooltip placement is patched.** Upstream `Modal.js` positions the bubble with a hardcoded assumed height and no on-screen clamping, which throws tall tooltips off the top of the screen. The patch measures the real height, clamps the tooltip on-screen, and adds two **opt-in per-zone props**: `tooltipBelowZone` (force placement beneath the zone) and `legacyTooltipPosition` (keep upstream math). Any new positioning behaviour should stay **opt-in per zone** — changing the shared math moves every step at once.
- `TourGuideZone` forwards only a **fixed allowlist** of props to the step (see `lib/components/TourGuideZone.js`); a new per-step prop must be added there too before `currentStep` will see it.
- Zones inside `@gorhom/bottom-sheet` and zones using `style={{ flex: 1 }}` measure poorly (relative to the sheet, or as the whole screen), which is why their tooltips need explicit placement props.
- `getTooltipPositionStyle` in `TourTooltip.tsx` is **dead code** (never called) — an abandoned earlier attempt at the fix above. Do not assume it affects layout.
- To retest the tour on an existing account use `resetTour` from `TourStepContext`; it is otherwise gated behind `user.hasCompletedTour`.

- `models/User.ts` — unused; user/profile types come from `constants/interfaces.ts`.

## UI & styling conventions

- **Responsive scaling:** use `moderateScale`, `horizontalScale`, `verticalScale`, `getWidth`, `getHeight` from `constants/Constants.ts` (reference frame 430×932) instead of raw pixel values.
- **Colors** → `constants/Theme.ts` (`Colors`). **All user-facing strings** → `constants/Strings.ts` (`Strings`). **Shared interfaces** → `constants/interfaces.ts`.
- **Path alias:** `@/*` maps to the repo root (`@/components/...`, `@/services/...`).
- **SVGs** are imported as React components (`react-native-svg-transformer`; metro moves `svg` from asset → source ext). Icons live in `assets/svg/`, typed via `declarations.d.ts`.
- **Fonts** load through `context/FontContext.tsx` (`FontProvider` blocks render until fonts resolve) + `utils/Fonts.ts`.
- **Forms:** Formik + Yup; validators in `utils/validators/`.
- **Toasts:** call the helpers in `utils/Toast.ts` (`showSuccessToast`, `showErrorToast`, `showInfoToast`) rather than `Toast.show` directly; rendering is `react-native-toast-message` with the custom `utils/ToastConfig.tsx` mounted in the root layout.
- **Global loader:** `components/Loader.tsx` is mounted once in the root layout and driven **imperatively** via the exported `showLoader()` / `hideLoader()` (module-level singleton, not Redux/props). It auto-hides after 15s as a safety net.
- **Bottom sheets:** `@gorhom/bottom-sheet`.
- **Beware stray `{" "}` in JSX.** A bare string as a direct child of a `View` throws *"Text strings must be rendered within a `<Text>` component"* at runtime — it renders as an error toast rather than a build failure, and one always-mounted instance makes it look like it belongs to whatever screen you are on. Several such literals exist inside `<Text>` (harmless); check the parent before copying the pattern.
- Prefer `minHeight` over a fixed `height` on containers holding user-supplied text (meal/ingredient names). A fixed height clips wrapped text and lets absolutely-positioned children — e.g. a remove "✕" — spill outside the box.
